### Fixed

- With the relay switched off on a vault that was using it, the next sync runs through the git backup and the vault's tree is byte for byte what it was: nothing removed, nothing rewritten.
- The doctor names the fallback in one line on the backup check it already reports: the relay is off, on but unreachable, or on but not running (the daemon is stopped, or `MEMEV_NO_TUNNEL` holds it off), so the relay address does not reach the vault while the git backup still carries its notes to your other computers, and `memev cloud relay on` switches the relay back on. A first connect still under way is not reported. The line is not added to the resume card or the protocol, and no new check id is added.
- With the relay configured but unreachable, the client reports the failure, reconnects on a growing pause (half a second, doubling up to a minute), and never blocks the daemon's other background jobs. An attempt the relay has not accepted in ten seconds is dropped and the drop is logged, so a non-routable address, or a relay that takes the connection and never answers, fails the same way a refused port does. `docs/RELAY.md` documents the fallback to the git backup.
