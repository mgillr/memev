### Added

- A trust record, version 1 (`memev-trust/1`), with its validator and schema (`docs/schemas/trust-record-v1.json`), and a pure `evaluate` that answers whether a subject is eligible for a purpose (contribute or verify) in a scope as of a stated time. It denies by default, lets delegation only narrow (the same scope, the same or fewer purposes, no later expiry, no earlier start, a lower depth), and applies a revocation from its time and cascades it to every grant delegated from the revoked one. Every decision carries a rule id from one fixed, exported set. Roots are a parameter, there is no default root, and the module reads no clock, file, network or source of randomness. Trust is an eligibility input only: it never grants a permission, a membership or a read, and a personal scope is never shared. The record format is provisional (the two purposes, narrowing-only delegation and who may revoke are proposals in ADR 8, which is proposed), and the module is a library with tests that nothing calls yet.
- The first review of the trust record fixed four ways it failed open, and made its tests fail by assertion before the code exists. A record of kind revocation that fails the validator and names a grant now denies that grant and every grant delegated from it (`deny.bad_revocation`), where it was dropped and the grant stayed allowed. Canonically equal grants now count once, so replaying a log is idempotent, and different grants with one id deny with their own rule (`deny.conflicting_grant`). `evaluate` and `validateTrustRecord` copy every input once with `structuredClone` and use only the copy, so a getter runs once and an input that cannot be read is a deny, and every time comparison fails closed on a time that is not a number. A time must be a real calendar date and time (no `2026-02-30`, no `T24:00:00Z`). Where several grants deny at the same stage the answer no longer depends on the order of the records: the rule listed first in `RULES` wins, then the chain that sorts first. The module header and the schema now say that the subject and issuer are unauthenticated strings and that the caller evaluates over its own log with a resolved actor and a credential-resolved subject, and that `scope.parent` is ignored by the evaluation. These are still provisional choices inside the contract.
- The second review of the trust record changed five things. A malformed revocation now counts against a grant only when its issuer could have revoked it: the issuer of the grant or a root, or an issuer that cannot be read as a subject id. A malformed revocation by a well-formed stranger is ignored, as a valid one is, so a bad record no longer beats a good one. A revocation must name its grant exactly, and a record whose target cannot be read (a number, a list, a trailing space, another case, a kind that is not exactly `revocation`) cannot revoke anything and is ignored, because failing closed on it would let one unreadable record deny every grant; callers must validate records before appending them. Grants that evaluation cannot tell apart now count once (the purposes as a set, the same instant in another zone, a different `scope.parent`, different evidence, no delegation block against depth 0), while a real difference still conflicts, and re-issuing a renewed grant under the same id is a permanent deny. A list with a hole in it (purposes, evidence, roots or records) is refused. A test now fails if the fixed order of the rules is removed from the choice among denies. These are still provisional choices inside the contract.
